Architecture

Two versioned seams

The three repositories depend on each other in one direction only. Each seam is versioned and machine-readable, so a change on one side cannot silently break the other.

CALLER (token contract, issuer, operator) │ │ screened operation: register · deposit · transfer │ transfer_from · merge · withdraw ▼ ┌──────────────────────────────┐ │ safeguard-hooks (ENFORCE) │ │ compliance-hooks contract │ │ │ │ cheap local gates first, │ │ then one policy call per │ │ screened party │ └──────────┬───────────────────┘ │ is_authorized(account, token) -> bool │ ── SEAM 1: versioned policy interface ── ▼ ┌──────────────────────────────┐ │ safeguard-policy (DEFINE) │ │ policy contract + engine │ │ │ │ account status (structural) │ │ allowlist → denylist → │ │ sanctions → jurisdiction │ └──────────┬───────────────────┘ │ compliance events (policy_created, │ rule_registered, policy_activated, │ token_bound, AdminSet, …) │ ── SEAM 2: versioned compliance events ── ▼ ┌──────────────────────────────┐ │ safeguard-audit (VERIFY) │ │ ingest → normalize → index │ │ → integrity chain → report │ └──────────────────────────────┘

The decision engine

Every evaluation resolves to exactly one of APPROVE, BLOCK or FLAG. The checks run in a fixed, documented order and the first decisive outcome wins — later checks never run.

OrderGateDecisive when
1Account status (structural)frozen or suspended → BLOCK; restricted or unknown → FLAG
2Allowlistrequired but not a member
3Denylistsubject is listed
4Sanctionsscreening produced a match
5Jurisdictionregion is restricted, prohibited or unknown
6otherwiseAPPROVE with no_reason

Account status is structural because the semantics are uniform: a frozen account is blocked regardless of how a policy is worded. That is why a structural outcome carries no rule id.

Fail-closed posture

Missing information never silently approves.

SituationResult
Unknown account statusFLAG account_status_unknown
Unknown jurisdictionthe rule's action — BLOCK under a blocking rule
Token not bound to an active policyevaluation refused / is_authorized answers false
Policy contract unreachabledenied (policy_unavailable)
Unknown status or region code sent by a callermaps to the Unknown variant, so junk input flags rather than widening outcomes

Error codes are assign-only

Reason codes and contract error codes are public API. They are quoted in stored records, in reverted transactions and in incident reports, so they are never renumbered and never reused. A removed variant keeps its number in a retired list rather than freeing it for a new meaning.

CodeLayerMeaning
2hooks contractUnboundToken — the token is not bound to this contract
3hooks contractPolicyDenied — the configured policy denied an account
4hooks contractAccountFrozen — an account holding funds is frozen
5hooks contractSpenderNotAuthorized — the spender of a delegated flow is denied
8hooks contractSacAuthorizationFailed — the underlying SAC check failed
9hooks contractInvalidConfiguration — configuration invalid or absent
10hooks contractPolicyUnavailable — the policy contract could not be reached
12hooks contractAlreadyInitialized — initialize called twice
1000+audit librarythe audit taxonomy, registered in errors/catalog.json and gated in CI

The hook codes are non-dense by design: removed codes are never reissued, so a number observed in the field never shifts meaning. The full audit table is generated from source and checked on every CI run.
